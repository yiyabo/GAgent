# 用户旅程验收脚本：医学临床数据分析（二甲双胍与 2 型糖尿病肾功能）

> 执行方式：computer use 驱动 agent.medicalheart.cn 真实界面，执行者扮演用户逐轮输入。
> 每轮 = 用户话术（逐字输入）+ 预期行为 + 检查点（判定标准）+ 常见失败模式。
> 判定纪律：检查点全部写出"看到什么算过"，不允许"感觉还行"算过；任何一轮失败即记录并继续，最后汇总。
> 测试数据：`../fixtures/diabetes_cohort.csv`（确定性生成，真值见附录 A，复生成：`python3 ../fixtures/generate_fixtures.py`）。

## 全局说明

- 测试账号：临时注册（见 README）；用全新账号保证无历史会话污染。
- 计时：每轮记录"发送 → 最终答复完成"的墙钟；execute 级允许 3~15 分钟。
- 截图：每轮结束截一张（最终答复 + 右侧交付物面板）；文件命名 `tNN_<阶段>.png`。
- 后端交叉验证：T6/T7 后可拿会话 id 到 .8 `runtime/<session>/deliverables/` 核对落盘文件（可选但推荐）。

## T0 注册/登录

- **操作**：打开 https://agent.medicalheart.cn，走注册流程建新账号并登录。
- **检查点**：注册成功进入主界面；无报错；左侧会话列表为空。
- **常见失败**：注册接口 500、验证码不发、登录后白屏。

## T1 模糊开场（路由分层 + 澄清能力）

- **用户输入**：`你好，我想研究二甲双胍对2型糖尿病患者肾功能的影响，我手头有一些临床数据，大概一百多个病人，有基线和随访的指标。这个能分析吗？`
- **预期**：正确识别为 research/execute 类意图；给出可行路径（可以分析 + 需要哪些数据/字段 + 建议的产出形态）；**不直接乱调工具**；提示可上传数据文件。
- **检查点**：①答复明确表示"可以分析"并说明需要什么数据字段；②没有无依据的具体数字结论；③整轮耗时 <120s。
- **常见失败**：当成闲聊只回两句客套；上来就 web_search 跑偏；编造"通常这类数据长什么样"的具体数字。

## T2 需求确认（上下文理解 + 路径建议）

- **用户输入**：`数据是csv，120个病人，分二甲双胍组和对照组，每组60人。有年龄、性别、BMI、HbA1c、eGFR、肌酐的基线和随访值，还有合并症和吸烟史。我想要的产出是：1）两组肾功能变化的对比分析；2）相关的图表；3）最后一份研究报告。你看怎么安排比较好？`
- **预期**：准确复述需求要素（120/60+60、字段、三个产出）；给出明确的执行安排（数据体检→统计对比→可视化→报告）；建议建结构化计划或直接说明执行步骤。
- **检查点**：①三个产出要素全部被接住；②字段理解无错（eGFR=肾功能核心指标）；③提出"建计划"或"直接执行"的清晰下一步。
- **常见失败**：漏掉"图表"或"报告"要素；把 eGFR 当成别的指标；建议里出现不存在的功能名。

## T3 任务构建（plan_operation 契约）

- **用户输入**：`好，那就建个计划开始执行吧。数据文件我马上传给你。`
- **预期**：调用 `plan_operation` create 生成结构化计划；计划任务覆盖：数据上传/体检→统计分析→可视化→报告撰写；给出 plan_id 和任务清单；说明等待数据上传。
- **检查点**：①答复中出现 plan_id（或"计划已创建"+任务列表）；②任务结构合理（≥3 个任务且顺序正确）；③没有假装已经拿到数据。
- **常见失败**：只用 markdown 写个"伪计划"不调 plan_operation（本轮特有的契约失败模式）；计划任务与实际需求脱节。

## T4 文献检索（web_search/literature 工具 + 溯源）

- **用户输入**：`在建计划分析之前，先帮我查一下近两年二甲双胍对糖尿病患者肾功能（eGFR、白蛋白尿）影响的最新研究，重点要RCT或者真实世界研究的结果，给我出处。`
- **预期**：调用 web_search / literature_pipeline；总结 2~4 篇相关研究的方向性结论（改善/中性/延缓下降）；**附可验证的 URL**；明确说明哪些结论来自哪篇。
- **检查点**：①答复含 ≥1 个 http(s) 链接；②结论方向与文献一致（二甲双胍对肾功能为保护或中性，不恶化）；③没有不附出处的具体断言（如"xx 研究证实 eGFR 提升 3.2"）。
- **常见失败**：只给结论不给链接；编造不存在的论文/DOI；把 2010 年前的旧闻当"最新"。

## T5 数据上传 + 基线分析（文件链 + 统计正确性）

- **操作**：通过界面附件功能上传 `fixtures/diabetes_cohort.csv`。
- **用户输入**：`文件传好了，是 diabetes_cohort.csv。先做个数据体检：确认行数、各组人数、有没有缺失值，然后算一下两组 eGFR 随访相比基线的平均变化（下降幅度），保留两位小数。`
- **预期**：file_operations/result_interpreter 读取并确认结构（120 行、60+60）；缺失值统计；分组计算 eGFR 变化均值；**数字正确**（真值见附录 A）。
- **检查点**：①行数 120、每组 60 被明确说出；②eGFR 平均下降：二甲双胍组 **2.65**、对照组 **3.57**（±0.05 容差，保留两位小数）；③缺失值结论正确（本数据集无缺失）；④明确提及对照组下降更多。
- **常见失败**：行数报错（119/121）；两组数字算反；缺失值瞎报；走 code_executor 失败后不换路径直接投降。

## T6 CJK 图表（科学画图 + 中文标签 + 内联渲染）

- **用户输入**：`把两组基线和随访的 eGFR 画成对比图：左边分组箱线图（基线 vs 随访），右边两组平均下降幅度的柱状图，中文标题和坐标轴，300dpi，输出 PNG。`
- **预期**：scientific_figure_generator 或 code_executor 出图；PNG 产出并在答复中**内联显示**；中文标签正常（非方块）；图中信息与 T5 数字一致。
- **检查点**：①答复里有内联图（不是光秃秃的文件名/链接）；②图非空白；③中文无方块；④柱状图数值≈2.65/3.57；⑤右侧交付物面板可见该图且能打开。
- **常见失败**：图片 404（路径错误）；中文方块（字体未注册）；只给文字描述不出图；画成英文标签。

## T7 研究报告（长文档交付 + 数字一致性）

- **用户输入**：`基于前面的分析和文献，写一份完整的研究报告（markdown）：背景与目的、数据与方法、结果（含统计表）、图表说明、结论与局限。结果部分的数字必须和我们算出来的一致。`
- **预期**：产出 markdown 报告文件（deliverables/）；包含全部指定小节；结果数字与 T5 一致（2.65/3.57、120/60+60）；引用 T4 的文献；局限部分提到观察性数据/未随机化（本数据为合成队列）。
- **检查点**：①报告文件存在且可打开；②五个小节齐全；③关键数字与真值一致（抽查 2.65 与 3.57 出现）；④字数 ≥1200 字；⑤答复中明确告知报告已保存及文件名。
- **常见失败**：只在聊天框里写报告不落盘；数字与分析阶段不一致；小节缺失；把合成队列写成"随机对照试验"。

## T8 审核资料 + 图表微调（差分修改能力）

- **用户输入**：`图我看过了，整体不错，就是字有点小——把标题和坐标轴字体都调大一些，其他不要动，直接覆盖原图。报告第三部分（结果）再把两组HbA1c的变化也补进去，二甲双胍组降1.02、对照组降0.31，顺便在结论里加一句对临床用药的提示。`
- **预期**：**差分微调**（不重画数据、保留其他元素）覆盖原图；报告增补 HbA1c 结果（1.02/0.31）+ 结论加临床提示；两个交付物都更新。
- **检查点**：①图被覆盖更新（同文件名）且字体明显变大、其他元素不变；②报告中出现 1.02 和 0.31 两个数；③没有重新跑全部分析（观察是否无脑重做 T5-T7）。
- **常见失败**：重画导致数据/样式变化；另存新文件造成新旧两份；报告改丢原有内容。

## T9 收尾与历史回看（会话持久性）

- **操作**：新开一个页面/刷新，重新进入本会话。
- **检查点**：①历史消息完整（各轮答复还在）；②T6 的图仍能打开渲染（不 404）；③T7/T8 的报告仍能下载/查看；④右侧交付物面板列出全部产物。
- **用户输入**：`把这次研究最终交付的东西列个清单给我。`
- **预期**：列出：对比分析数字、对比图 PNG、研究报告 md（及其修订版）；与实际落盘一致。
- **常见失败**：刷新后图全挂（路径/会话隔离问题）；清单里出现不存在的文件。
