# GAgent PhageScope V2 Read-Only Data Service

Self-contained read-only service owned by GAgent (`/data3/platform/gagent/phagescope-service/`).
Requires **zero modifications** to PhageScope's website codebase or PostgreSQL tables.

## Safety Guarantees

1. Connects strictly as `phage_ro` (`NOSUPERUSER`, `default_transaction_read_only=on`, `statement_timeout=10000ms`, max 4 pooled connections).
2. Startup self-check verifies `INSERT`, `UPDATE`, and `DELETE` privileges on `phages` are all `False`; exits immediately otherwise.
3. Binds `127.0.0.1:18326` on the host and requires constant-time `X-API-Key` validation. `gagent-forwarder-1` exposes `18326` only on the internal Docker bridge (`FORWARD_BIND`).
4. Serves both legacy `/agent-api/v1/data/*` GET endpoints (`phagescope(action="gateway")`) and research-grade `/agent-api/v1/data/v2/*` POST endpoints (`phagescope_data`).

## Private Parquet snapshot (Phase 2, opt-in)

`app/services/phagescope_data_service/{server.py,db_queries.py,accel_engine.py}` are the host service sources; install all three together. `scripts/build_phagescope_accel.py` reads PostgreSQL as `phage_ro` in a repeatable-read, read-only transaction and scans only filenames from the sequence trees. Build with a **new version name** (for example `v2`); it refuses existing versions and updates `current` with an atomic symlink replacement only after row-count, uniqueness, count-sum, and SHA-256 checks. The earlier exploratory `v1` is not a Phase 2 release artifact. A failed build leaves `current` at its previous target.

The version contains `phages_wide.parquet` (seven per-phage annotation-count columns and dataset-scoped FASTA/FAA/GFF3 availability bits) plus `manifest.json` with `format_version=2`. In the source catalog, 22,720 accessions occur in both IMG_VR and MetaVR. AMR, VFDB, anti-CRISPR, and transmembrane counts are joined by dataset and accession (or numeric phage ID for tRNA). The CRISPR and terminator sources have no dataset key, so both counts are **null/unknown** for those duplicated accessions; predicates must never treat unknown as zero. The manifest records `annotation_unknown_rows`, `ambiguous_accessions`, and `uncatalogued_source_features` (feature rows with no catalog accession, excluded from the snapshot with per-track counts). If a feature row names an accession present under a different dataset, publication fails rather than recording a false zero. Feature-level `features/*.parquet` is deferred: this release exposes catalog-level counts only. A zero annotated CARD/VFDB hit is **not** evidence that a phage is clinically safe. The availability bitmap describes files at build time; the materializer checks real files and can fall back to the database, and a capped preview is never labeled a full genome.

Until a validated v2 build is published, leave host `service.env` without `PHAGE_ACCEL_ROOT` and leave app `deploy/.env` without `PHAGESCOPE_ACCEL_HOST_DIR`. Normal catalog queries continue through PostgreSQL. After validating live SQL parity and file samples, set `PHAGE_ACCEL_ROOT=/data3/platform/gagent/phagescope-accel/current` in the host service environment and `PHAGESCOPE_ACCEL_HOST_DIR=/data3/platform/gagent/phagescope-accel` in the app environment. Back up both configuration files with mode 0600, restart the host service and deploy the app through `gagentctl` after `gate`. New filters/multi-dimensional groups need the validated build; ordinary queries keep their SQL behavior. `execute_code` receives only the GAgent-owned Parquet root as a read-only bind (also allowlisted by the Docker proxy) and exposes `phagescope_dataset` / bounded `phagescope_dataframe` helpers through generated `gagent_tools` stubs. Roll back by removing these two environment variables, restoring the backed-up service files, and restarting normally; keep the immutable Parquet versions for audit.

## Private protein-family FTS5 snapshot (Phase 3)

`app/services/phagescope_data_service/family_fts_engine.py` joins the three host service modules above. `scripts/build_phagescope_family_fts.py` uses only `phage_ro` in a read-only repeatable-read transaction. It streams families with a nonblank `consensus_product` or `dominant_class` into a GAgent-owned SQLite FTS5 database; the entire 12.61M-family source count and the indexed subset count are reconciled in the manifest. The snapshot holds family search metadata and text, with no protein sequences. The `family_synonyms.json` file is a versioned, small alias list under `deploy/phagescope_data_service/`; aliases aid retrieval and do not establish biological function. The builder validates FTS5 and SQLite integrity, row counts, read-only reopen, and SHA-256 before switching `current` atomically. A failed build leaves `current` intact.

On 620b, copy the builder and synonym file to a GAgent-owned staging directory, then build a **new** version (the command requires an existing output directory):

```bash
python3 build_phagescope_family_fts.py \
  --service-env /data3/platform/gagent/phagescope-service/service.env \
  --synonyms /data3/platform/gagent/phagescope-family-search/family_synonyms.json \
  --out-root /data3/platform/gagent/phagescope-family-search \
  --version v3
```

After checking the manifest and sample queries, install `family_fts_engine.py` beside `server.py`, `db_queries.py`, and `accel_engine.py` in the GAgent host service; add `PHAGE_FAMILY_INDEX_ROOT=/data3/platform/gagent/phagescope-family-search/current` to its `service.env` and restart. No app mount or PostgreSQL change is needed. With the index configured, a family keyword defaults to indexed word/phrase matching across product and dominant class (`family_search_mode=auto`). `family_search_mode=synonyms` searches the curated aliases and marks `match_kind=literal|alias`; `family_search_mode=literal` preserves the original PostgreSQL substring query. `family_search_mode=fts` requires the index. Indexed results report `source`, `search_mode`, and `index_built_at`; the snapshot can lag a live database update. Direct `family_id`/`protein_id` queries, members, and searches without a keyword still use read-only PostgreSQL. A configured but invalid index yields `503 family_index_unavailable` for indexed requests. Roll back by removing the family root environment variable, restoring the previous host service modules, and restarting; keep immutable versions for audit.

### Daily family-index freshness check

Install `app/services/phagescope_data_service/family_freshness.py` beside the host service modules and the two GAgent-owned user units `deploy/phagescope_data_service/gagent-phagescope-family-check.{service,timer}` under `~/.config/systemd/user/`. `systemctl --user daemon-reload`, start the oneshot once, then `systemctl --user enable --now gagent-phagescope-family-check.timer`. The timer runs daily at 04:30 host local time (up to 15 minutes of random delay). It reads `phage_ro` with a 20-second statement timeout, checks full and indexed row counts plus 256 spread-out family annotations, and writes `/data3/platform/gagent/phagescope-family-search/family_freshness_status.json` atomically with mode 0600. A detected drift exits 2; an unavailable source/index exits nonzero. Inspect `systemctl --user status gagent-phagescope-family-check.service` for failures.

`phagescope_data(operation="family_index_status")` and the authenticated `GET /agent-api/v1/data/v2/proteins/family-index/status/` return the most recent report without querying PostgreSQL on every request. `matched_counts_and_samples` describes **observed** agreement only; it does not prove every annotation remained unchanged. Missing, invalid, mismatched-version or older-than-36-hour reports return `not_checked`, `invalid_report`, `version_mismatch` or `check_overdue` instead of a green status. When drift is detected, investigate the source changes and build a **new** immutable version with `build_phagescope_family_fts.py`; verify the manifest and sample queries before switching `current`, then restart the host data service so it pins the new version. To roll back the checker, disable its timer, restore the previous service modules, and retain the last status report for audit.

### Bounded search-quality review

`deploy/phagescope_data_service/family_search_eval_queries.json` contains 20 versioned canonical, alias, and ambiguity-control queries. On the GAgent host, run `scripts/evaluate_phagescope_family_search.py` with `--service-env`, `--index-root`, `--queries`, and a **new** `--out-dir` inside the private family-search directory. It executes only bounded first-page `literal` PostgreSQL, `fts`, and `synonyms` queries. The result directory contains `results.json`, `summary.md`, and `review_candidates.tsv`; `expert_label` and `expert_note` are intentionally empty. A timed-out SQL query is recorded as an error, not counted as zero hits. Freeze expert judgments before calculating precision or recall, and investigate generic motif names or contextual mentions before expanding the alias list. These one-off timings are diagnostic samples, not a service latency SLO.

## Protein similarity search (MMseqs2)

`similarity_engine.py` serves `POST /agent-api/v1/data/v2/similarity/search`, `GET /agent-api/v1/data/v2/similarity/search/{search_id}` and `GET /agent-api/v1/data/v2/similarity/status`, which back the MCP tools `similarity_search` and `get_similarity_result` (design: `design/2026-11-20-phagescope-similarity-search.md`). An index version under `/data3/platform/gagent/phagescope-similarity/<version>/` holds `db/base` (30–2700 aa unique proteins), `db/long` (>2700 aa supplement), `db/members.sqlite` (seq_md5 → protein id and source dataset, derived from the same protein FASTA files as the index) and `manifest.json` (counts, MMseqs2 version, file sizes and SHA-256). Proteins under 30 aa are not indexed. Hits therefore follow the FASTA files' sequence version; about 1.3% of PostgreSQL `unique_seq` rows hold a different gene call and are not used for expansion. Startup checks the manifest and file sizes; a configured but invalid index yields `503 similarity_unavailable`.

Install `similarity_engine.py` beside `server.py` and set in `service.env`: `PHAGE_SIMILARITY_ROOT=/data3/platform/gagent/phagescope-similarity/current`, `PHAGE_SIMILARITY_MMSEQS=/data3/platform/genefamily/envs/genefamily/bin/mmseqs`, and optionally `PHAGE_SIMILARITY_WORK_DIR` (default `<root>/../jobs`), `PHAGE_SIMILARITY_RUNNER=slurm|local` (default `slurm`: `sbatch --wait` on `PHAGE_SIMILARITY_PARTITION`, default `work`, 16 CPU, `PHAGE_SIMILARITY_SLURM_MEM`, default `32G`). Searches are cached by index version, sequences and parameters for 7 days; at most 2 run at once and 20 are pending (`429 too_busy` beyond that). Each response carries `status` (`queued` until the job script starts, including Slurm pending time; then `running`, `done` or `failed`) and `outcome` (`pending`, `hits`, `no_hits` or `failed`); `count` and per-query `hits` are `null` until `status=done`, so a pending or failed search never reads as zero hits. `timings` gives `queued_seconds` (data-service slot plus Slurm pending), `run_seconds` (from the job script's start marker) and `total_seconds`; each finished search also logs one `Similarity search <id> <status> queued=… run=… total=…` line. A run that hits the Slurm time limit (15 min) or the 20-min service timeout fails with `error.code=search_timeout`, other failures with `search_failed`. Each search mmaps the whole precomputed index (`db/base.idx` is 92 GiB) and a Slurm job's memory cgroup is charged for every index page it faults in, so against a cold page cache a single query thrashes under the 32G cap on the rotating `/data3` disk and hits the time limit. The data service therefore keeps `db/*.idx` in the page cache itself (`PHAGE_SIMILARITY_KEEP_WARM`, default on; `0` turns it off): at startup and every 5 minutes it checks residency with mincore(2) and re-reads the files sequentially when less than 99% is cached (a cold read takes about 15–25 min at the disk's ~70–100 MB/s). Pages cached by the data service are not charged to the job, so warm searches finish in seconds under 32G. While less than 90% is resident, searches stay `queued` with `waiting_for=index_loading` and are dispatched once the read finishes; after 40 min they fail with `error.code=index_loading`. `similarity/status` reports `index_cache` (`ready`, `warming`, `resident_fraction`, `last_warm_seconds`). Query sequences are written only to the job FASTA, which is deleted when the search finishes. Roll back by removing `PHAGE_SIMILARITY_ROOT` and restarting.

Each search keeps `jobs/<search_id>/job.json` (status, timestamps, error) from submission on and `result.json` (plus hits) once done. Both are kept 7 days from when the search finished (from submission if it never finished), across service restarts. A search that was queued or running when the service stopped reads back as `failed` with error code `interrupted`; submitting the same input again reruns it, while resubmitting a search that is still kept returns the kept run untouched.
